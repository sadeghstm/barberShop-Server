# بک‌لاگ (خارج از محدوده این نسخه)

موارد زیر طبق بخش ۸ سند طراحی عمداً پیاده‌سازی نشده‌اند. هر مورد جای مشخصی در کد دارد تا در
آینده بدون بازنویسی هسته اضافه شود.

| مورد | چرا الان نیست | نقطه اتصال در کد |
|---|---|---|
| درگاه پرداخت واقعی | سند: پرداخت شبیه‌سازی‌شده | `services/appointment.js` → `confirmWithPayment` (جای `Payment` با `provider: mock`) |
| برداشت از کیف پول | سند: کیف پول برداشت ندارد | `services/wallet.js` (نوع تراکنش جدید + مسیر ادمین) |
| انتقال نوبت به آرایشگر دیگر | سند: بک‌لاگ | `Appointment.barberId` عمداً `immutable` است؛ نیاز به عملیات ویژه + audit |
| انتخاب «اولین آرایشگر آزاد» | بک‌لاگ | `services/availability.js` + حلقه روی `barberServices` |
| Web Push / WebSocket | سند: FCM در ایران قابل اتکا نیست | `services/smsQueue.js` (کانال اعلان قابل افزودن) |
| استعلام واقعی پروانه کسب | سند: بک‌لاگ | `Shop.license` (وضعیت `disabled`) |
| چند نوبت هم‌زمان مشتری | سند: بک‌لاگ | قید فعلی: یک نگه‌داشتن فعال برای هر مشتری |
| جابه‌جایی خودکار نوبت‌ها هنگام تعطیلی | فعلاً تغییر مسدود می‌شود | `services/appointment.js` → `recalculateEstimated` + پیشنهاد جابه‌جایی |
| لغو دیرهنگام با کال‌بک پس از انقضای نگه‌داشتن | بک‌لاگ | `Payments.idempotencyKey` + وضعیت `expired` |
| گزارش‌های پیشرفته (درآمد ماهانه، عملکرد آرایشگر) | فاز بعد | `services/admin.js` → `getDailyStats` |

## کارهای فنی باقی‌مانده (نه قابلیت محصول)

- **ایندکس‌ها در محیط واقعی**: کاربر مونگوی برنامه باید دسترسی update/delete روی `auditLogs` نداشته باشد
  تا «فقط افزودنی» در سطح دیتابیس هم تضمین شود (توضیح در مدل `AuditLog`).
- **اجرای چند نمونه سرور**: زمان‌بند درون‌پروسه‌ای است؛ عملیاتش idempotent است ولی برای مقیاس افقی
  بهتر است به یک worker با قفل توزیع‌شده (مثلاً قفل ردیس روی `job:expire-holds`) منتقل شود.
- **نظارت (observability)**: لاگ‌های ساختاریافته آماده‌اند؛ افزودن متریک/health عمیق‌تر برای production.
- **تست یکپارچه با MongoDB/Redis واقعی**: تست‌های فعلی بدون دیتابیس اجرا می‌شوند (مدل‌های در حافظه)؛
  برای CI نهایی یک محیط docker-compose با `mongodb` و `redis` توصیه می‌شود.
